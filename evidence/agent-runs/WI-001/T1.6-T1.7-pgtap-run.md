## How this ran without the Supabase CLI

The CLI is not installed — verified, not assumed: not on `PATH` in either shell, `winget list
--id Supabase.CLI` reports no installed package, and no binary in the WinGet, scoop or chocolatey
link directories. Docker is absent too, so there is no local stack.

`supabase test db` is a runner: it pipes `.sql` files through `pg_prove`. **pgTAP itself is a
PostgreSQL extension**, and the assertions are ordinary SQL functions. Both are available on this
project — `pgtap 1.3.3` and `plpgsql_check 2.8` appear in `pg_available_extensions`, which also
closes the item `work/WI-001/RESEARCH-SLICES.md` §5 carried as *unverified*.

pgTAP was installed with `create extension pgtap with schema extensions` through `execute_sql`,
**not** through `apply_migration`. The product migration stream stays product-only; a test framework
is an environment fixture, and installing it into the schema history would put a test dependency
into the qualified baseline.

The suite runs inside `begin … rollback`, verified to work through this transport with a probe row
that did not survive. That is not tidiness: `audit_trail`, `signature` and `security_event` refuse
`DELETE` and `TRUNCATE` by design, so a suite that committed its fixtures would leave permanent
residue in a GxP table with no way to remove it.

## What the run proves

Fourteen assertions across the three session-context requirements, the redaction control, Layer 2
append-only enforcement **against the owner**, Layer 3 `TRUNCATE` refusal, the `ENABLE ALWAYS`
conformance count, and `URS-FUNC-001`.

`finish()` emitted no diagnostics. That is meaningful rather than inferred: an earlier run of the
same suite emitted `# Looks like you failed 1 test of 14`, so the function does report on failure
through this transport. An empty `finish()` means the plan matched and nothing failed.

## The assertion that was wrong before it was right

`URS-FUNC-001` is enforced by a **deferred** constraint trigger, so the offending `INSERT` does not
raise — the check runs at commit. A `throws_ok` wrapped around the insert reported
`caught: no exception`.

The trap is not that the test failed; it is what a hurried fix would have been. The schema is
correct — T1.5 recorded the commit being refused on this same instance. Making the test pass by
loosening the trigger would have destroyed the requirement to satisfy the test. The correct form
forces the constraint immediate inside the transaction, and that is what the suite now does, with
the reason written beside it so the next person does not re-derive it.

A second discarded assertion tried to check post-rollback state from inside the transaction, which
cannot work; it was removed rather than weakened.
