# T1.2 (partial) — the `ADR-EREC-001` handshake, SQL half, on the live instance

**Work item**: WI-001 · **Task**: T1.2 · **Date**: 2026-08-02
**Target**: hosted Supabase project `aiqms`, region `eu-west-1`, PostgreSQL 17.6.1
**Transport**: Supabase management API (`execute_sql`) — **not** the pooler, **not** psycopg 3

## What this run covers, and what it does not

`work/WI-001/IMPLEMENTATION-PLAN.md` T1.2 has two halves. This run executes the **SQL half** — that
the session-context handshake behaves as `ADR-EREC-001` describes, on a real PostgreSQL 17 instance,
rather than as reasoned from documentation.

**It does not close T1.2.** The second half — that the handshake survives **Supavisor in transaction
mode** with a **psycopg 3** connection and `prepare_threshold=None` — requires a direct database
connection and is still outstanding. `work/WI-001/RESEARCH-SLICES.md` §1 rates the pooler as the
specific risk, so the untested half is the risky half. Nothing here may be cited as evidence that
the pooler preserves the settings.

The vehicle was created in a `scratch_handshake` schema through `execute_sql`, never through
`apply_migration`, and dropped at the end of the run — `pg_namespace` confirms zero remaining
objects. It is absent from the migration stream by construction, as the plan requires.

## Results

| # | Assertion | Result |
|---|---|---|
| 1 | A trigger created and then `ALTER TABLE … ENABLE ALWAYS TRIGGER` reports `pg_trigger.tgenabled = 'A'` | **Pass** |
| 2 | A write inside a transaction that has set all three settings is trailed with the correct actor, reason and zone | **Pass** — `actor_id`, `reason = 'Opening the deviation'`, `tz = 'Europe/Madrid'` |
| 3 | `current_setting('aiqms.actor_id', true)` and its two siblings are **null** at the start of a fresh transaction | **Pass** — all three null, one trail row persisted |
| 4 | A write with no `aiqms.actor_id` is **rejected**, not recorded as unattributed | **Pass** — `P0001 AIQMS_NO_ACTOR … (URS-EREC-013)` |
| 5 | A write with an actor but no `aiqms.reason` is rejected | **Pass** — `P0001 AIQMS_NO_REASON … (URS-EREC-005)` |
| 6 | A write with actor and reason but no `aiqms.tz` is rejected | **Pass** — `P0001 AIQMS_NO_TZ … (ADR-DATA-002)` |
| 7 | Under `session_replication_role = 'replica'`, an `ENABLE ALWAYS` trigger still fires | **Pass** — same `AIQMS_NO_ACTOR` rejection |
| 8 | **Control**: under the same setting, an *ordinary* trigger is skipped | **Pass — and this is the finding** |

Assertion 3 is the one that matters most and is easiest to get wrong. `set_config(…, true)` is
transaction-local; a session-level setting would survive onto a connection handed to another client
and attribute a write to the wrong user — a record that is complete, plausible and false, the
lowest-detectability failure class in `specs/RA-INIT.md` §3.4.

## Finding — `ENABLE ALWAYS` is load-bearing, and its absence fails silently

Assertions 7 and 8 were run as a matched pair because assertion 7 alone would have been vacuous: if
`session_replication_role = 'replica'` had not taken effect, the trigger firing would prove nothing.

The control makes it conclusive. A second table carried an **ordinary** trigger
(`tgenabled = 'O'`) whose function does nothing but `RAISE EXCEPTION`. Under
`set local session_replication_role = 'replica'`:

- the ordinary trigger was **skipped** — the insert succeeded, one row landed, no exception;
- `current_setting('session_replication_role')` read `replica`, so the mode was genuinely active;
- the `ENABLE ALWAYS` trigger on the other table **still fired** and rejected its write.

So the bypass is real, it is available to the role in question, and against an ordinary trigger it
is **silent**: writes land untrailed and nothing errors. A trigger-driven audit trail built without
`ENABLE ALWAYS` would appear to work and would be bypassable by one `SET`.

This confirms `work/WI-001/RESEARCH-SLICES.md` §2 Layer 2 on the live system and upgrades the
schema conformance test from prudent to mandatory: **`pg_trigger.tgenabled` must be asserted `'A'`
for every trigger in GxP scope**, because the failure mode of forgetting one `ALTER TABLE` produces
no error at any point.
