# T1.4 (partial) and T1.7 — the application role and the three immutability layers

**Work item**: WI-001 · **Tasks**: T1.4 (partial), T1.7 · **Date**: 2026-08-02

## What T1.4 covers here, and what it does not

`aiqms_app` exists, holds `SELECT` and nothing else, and its privilege model is **proven by
assuming the role** (`SET ROLE`). What is **not** proven is that it can *connect* through Supavisor
in transaction mode, which is the half `work/WI-001/IMPLEMENTATION-PLAN.md` T1.4 names as the stop
condition for `ADR-DATA-001`. That needs a direct connection string.

The role is deliberately created **without a password**, so as written it cannot authenticate.
Supabase requires password authentication; the password is set out of band and recorded in a
git-ignored `.env`. Putting it in the migration would publish a database credential — this
repository is public.

## The conformance test earned its place on its first run

`aiqms.trigger_conformance` reported **21 of 22** triggers `ENABLE ALWAYS`. The one that was not:
`trg_quality_record_detail_present`, the deferred constraint trigger created in the T1.5 migration
that makes `URS-FUNC-001` a property of the database.

So `URS-FUNC-001` was bypassable by one `set session_replication_role = 'replica'` — a spine row
with no detail row could have been committed, silently, with no error at any point. T1.2 had already
demonstrated on this instance that an ordinary trigger is skipped without complaint in that mode.

Twenty-one out of twenty-two is exactly the hit rate the test was written for: the failure is a
single missing `ALTER TABLE`, invisible to review, and fatal to the requirement it guards. Fixed in
`20260802130427`; the view now reports 22 of 22.

Assertions 5 to 8 matter more than 3 and 4. Layer 1 restrains the application role; it cannot
restrain the write-path functions, which `ADR-DATA-001` runs as the owner. Layers 2 and 3 are the
only layers that bind a defect inside a `SECURITY DEFINER` function, and 5–8 are the proof they do.

## A narrowing of the residual, verified rather than assumed

`work/WI-001/RESEARCH-SLICES.md` §2 records that no in-database mechanism defends against the table
owner or a superuser. On this platform the second half is narrower than feared: the role the
management API connects as is `postgres`, and `pg_roles.rolsuper` for it is **false**. Supabase does
not hand out superuser. The residual on this hosted platform is therefore the **owner**, not a
superuser available to the operator — and the owner is restrained by Layers 2 and 3 for everything
tested above.

That does not remove the residual; it re-describes it accurately, which is what the Design
Specification has to do. Credential custody for the owner role remains an environment control.

## Data state

One `app_user` (`reporter1`, Ana Reporter) and its four audit trail entries remain. They were
created through the session-context path with a real actor and reason, and they are now
**undeletable by construction** — `app_user` and `audit_trail` both refuse `DELETE`. That is the
intended behaviour and the first legitimate entry in the trail.
