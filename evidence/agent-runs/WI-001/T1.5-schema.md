## Deviation from the plan's task order, and why

T1.4 (the `aiqms_app` role) was planned before T1.5 and is **not** done. Proving that role can
connect *through the pooler* needs a database client, and the direct connection string is not yet
available. T1.5 is pure DDL, needs no client, and nothing in it depends on T1.4 — the privileges do,
and those are T1.7. T1.4 remains open with its stop condition intact.

## One implementation decision recorded

Objects live in a dedicated `aiqms` schema rather than `public`. The thin specs do not constrain the
schema name; a dedicated schema keeps the later `REVOKE`s independent of whatever `public` grants by
default. Reversible, and recorded here rather than left implicit.

## Results

| # | Assertion | Result |
|---|---|---|
| 1 | The migration applies cleanly to an empty database | **Pass** — `list_migrations` shows one entry |
| 2 | A `quality_record` inserted with no `deviation` row **cannot commit** | **Pass** — `P0001 AIQMS_INCOMPLETE_RECORD … (URS-FUNC-001)` raised by the deferred constraint trigger |
| 3 | Spine and detail inserted in one transaction commit, and the record lands in `Draft` with `severity` and `investigation_required` still null | **Pass** |
| 4 | A state absent from `record_state_catalog` is refused | **Pass** — `23503 quality_record_state_valid`, `Key (record_type, state)=(deviation, Closed) is not present` |

Assertion 2 closes the independent review's first finding against `THIN-SPECS.md` v0.1, where
`URS-FUNC-001` was an application rule with nothing beneath it. It is now a property of the
database: the trigger is `deferrable initially deferred`, so a write path may insert spine and
detail in either order within one transaction but cannot commit with only one.

Assertion 4 is the reason `record_state_catalog` is a table rather than an enum — state validity is
per Record Type, and the composite foreign key makes an invalid state unreachable even by a direct
write.

## Data state after the run

The rows created for assertions 2–4 were deleted. The audit trigger does not exist yet (T1.6), so
those rows carried no trail, and leaving untrailed rows in a GxP table would set exactly the wrong
precedent. The database now holds the schema, the six seeded catalog rows, and no data.
